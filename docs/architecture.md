# Устройство Ритма

Интерфейс — обычные HTML, CSS и JavaScript. Серверная часть — Python и SQLite. У локальной и облачной версий общие маршруты и модель данных.

```text
Telegram Mini App / браузер
          |
          v
server.make_handler — API, cookie-сессия, защита запросов, файлы
          |
          v
Store + RecurrenceStore — записи, правила повторений, отдельные изменения
          |
          v
SQLite — пользователи, сессии, серии и сохранённые записи
```

`server.py` запускает стандартный HTTP-сервер для локальной работы. `cloud_wsgi.py` создаёт WSGI application для хостинга. Адаптер `ritm/hosting.py` передаёт обычные запросы тому же обработчику, поэтому проверка подписи Telegram, доступ к данным и валидация форм не дублируются.

## Telegram и напоминания

На компьютере `run_telegram.py` запускает отдельный HTTP-сервер, временный HTTPS-туннель и получение команд через getUpdates. Напоминания проверяются в отдельном потоке, пока процесс работает.

На бесплатном хостинге команды приходят POST-запросом на `/telegram/webhook`. Проверяется секретный заголовок Telegram. Номер успешно обработанного обновления сохраняется в SQLite: повторный запрос не отправляет тот же ответ заново. Неудачная обработка возвращает 503, чтобы Telegram мог повторить доставку.

Cron-job.org вызывает POST `/internal/reminders` с отдельным ключом Authorization. Короткая блокировка в SQLite не позволяет запустить две проверки одновременно. За запрос отправляются максимум два уведомления, сетевые ожидания ограничены. Очередь и попытки доставки хранятся в основной базе.

Эти два входа не используют браузерные cookie и не требуют заголовка X-Ritm-Request. Вместо него у каждого свой случайный секрет. Остальные POST/PUT/DELETE проходят обычную защиту сессии и Origin. Настройки облака не разрешают деморежим.

## Данные

Каждая запись привязана к владельцу, которого сервер определяет по сессии. Идентификатор из формы не используется для выбора пользователя. Повторения вычисляются из правил в `ritm/recurrence.py`, а выполнение, удаление и разовые изменения сохраняются отдельно для конкретной даты.

День календаря хранится отдельно от точного времени. Время — UTC, у серии есть исходный часовой пояс IANA. В браузере интервалы показываются в часовом поясе устройства.

Локальный браузер использует `data/ritm.sqlite3`; Telegram — `data/telegram.sqlite3`. При переезде переносится именно Telegram-база. `.env`, `.env.cloud`, базы, резервные копии и загруженный cloudflared не входят в Git.

## Проверки

Тесты используют временные базы и имитируют Telegram API. Они проверяют подпись, раздельные профили, CRUD, повторения, графики занятости, повторную доставку, защиту webhook и WSGI. Реальную работу хостинга, меню Telegram и уведомления проверяют после подключения аккаунта; автоматические тесты не заменяют эту проверку.
# Размещение с PostgreSQL

На Render используется `PostgresStore` из `ritm/postgres.py`. Он использует те же методы работы с пользователями и повторениями, что SQLite, но открывает транзакции PostgreSQL через psycopg. Параметры SQL передаются отдельно от значений. Таблицы находятся в закрытой схеме `ritm`; браузерным ролям Supabase доступ не выдаётся.

`cloud_wsgi.py` выбирает базу по DATABASE_URL. На Render отсутствие этой переменной считается ошибкой, потому что локальный диск там временный. Для локального запуска и PythonAnywhere SQLite сохранена. Миграция переносит данные только в пустую целевую базу одной транзакцией.
